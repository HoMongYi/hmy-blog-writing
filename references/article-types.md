# Choose a Form for the Article

Writing type and subject are separate. First determine what the reader should understand, consider, or be able to do. Choose a form for the available material and the author's intended mood. Technology, daily life, economics, science, culture, hobbies, travel, and personal stories do not need separate rulebooks.

- **Experience and reflection:** Let confirmed scenes, actions, or thoughts carry the piece. An essay need not end with advice or a lesson.
- **Explanation and research:** Follow the reader's question. Separate established information from interpretation; add background only where useful.
- **Comparison and criticism:** Choose relevant criteria and connect judgments to evidence. Do not pretend to have used or witnessed something.
- **How-to and problem solving:** Order steps by prerequisites, safety, and what results mean. An unknown cause stays uncertain.

These are choices, not a closed taxonomy. An unlisted subject is not a reason to refuse or force a familiar template. Mixed forms can work: experience + explanation, review + buying judgment, research + opinion, devlog + trial and error, or daily record + essay. Shift form locally when needed while keeping one consistent voice.

## Representative Examples, Not the Support Limit

These ten cases illustrate possible flows, especially for practical and technical writing. They are not mandatory headings or the full support range.

| Example | Useful purpose | Possible flow |
| --- | --- | --- |
| Product / service review | Explain what mattered | Confirmed context → observations and tradeoffs → scoped judgment |
| PC assembly / repair record | Preserve a working record | Task → obstacle → action and result → relevant conditions |
| Troubleshooting | Narrow down a symptom | Symptom → plausible checks → interpretation → remaining uncertainty |
| Technical explanation | Explain a distinction or mechanism | Reader's question → mechanism → implications and limits |
| Software how-to | Help complete a task | Prerequisites and version → steps with reasons → result and exceptions |
| Server / system setup log | Record a reproducible setup | Goal → choices → confirmed steps → observed state |
| Devlog | Explain how a tool took shape | Actual motivation → decisions → recorded difficulties → present state |
| Product / service comparison | Compare fit for a purpose | Use case → relevant differences → conditions and judgment |
| Buying / selection guide | Connect criteria with a situation | Needs → constraints → alternatives and tradeoffs |
| Short information / tip | Answer a small question | Question → answer → necessary condition, if any |

Apply model/version/specification checks when those claims occur. A diary does not need a vendor manual. Do not force a uniform introduction, a quota of pros and cons, a summary table, or a ceremonial conclusion. End when the purpose is fulfilled.
